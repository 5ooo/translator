# 本机离线 OCR 对比测试

2026-11-23 在同一台电脑上比较中英文 OCR。测试目标是离线处理截图，并将检测和识别模型的总大小控制在 500 MiB 以下。当前工具根据模式使用 PP-OCRv6 Tiny 或 Small；模式对应关系见[模型选择](MODEL_SELECTION.md)。

| 方案 | 检测与识别模型 | 文字行相似度 | 整图相似度 | 单次 OCR 中位耗时 |
| --- | ---: | ---: | ---: | ---: |
| Tesseract fast（原方案） | 6.3 MiB | 55.5% | 91.9% | 0.27 秒 |
| Tesseract best | 27.2 MiB | 55.9% | 92.0% | 0.30 秒 |
| EasyOCR | 100.2 MiB | 43.7% | 95.8% | 5.20 秒 |
| PP-OCRv4 Mobile | 14.9 MiB | 92.7% | 99.7% | 1.26 秒 |
| PP-OCRv5 Mobile | 20.5 MiB | 94.0% | 99.4% | 1.15 秒 |
| PP-OCRv5 Mobile 检测与 Server 识别 | 85.3 MiB | 97.1%（45 条） | 98.9% | 4.59 秒 |
| PP-OCRv6 Tiny | 6.0 MiB | 94.5% | 99.6% | 0.72 秒 |
| PP-OCRv6 Small | 29.7 MiB | 97.4% | 100.0% | 1.64 秒 |

除 PP-OCRv5 Server 识别仅比较 45 条文字行外，其余方案均使用相同的 300 条文字行和 10 张整图。Small 在这批文字行上最好；Tiny 较小、启动较快。PP-OCRv4 在部分英文中漏掉词间空格，不能仅凭忽略空格的得分判断质量。Tesseract best 在这批低分辨率文字行上的提升有限。

## 测试方法与限制

从 [zh_en_rec_bench](https://huggingface.co/datasets/puhuilab/zh_en_rec_bench) 中抽取简体中文、英文和中英混合文字行各 100 条，图像高度为 8–101 像素。文字长度限定为 8–100 字符，图像宽至少 80 像素、高至少 8 像素且宽高比至少 1.5。先以随机种子 20261123 抽取 45 条，再以种子 20261124 从剩余样本中抽取 255 条。文字行测试只运行识别阶段；Tesseract 使用 `eng+chi_sim` 和单行模式 `--psm 7`。

整图包含 9 张生成的浅色、深色、中英混排、小字及终端截图，以及 1 张真实英文网页截图。整图测试运行文字检测和识别，Tesseract 使用默认 `--psm 3`。真实中文截图、手写、旋转文字和复杂多栏图片不在这批整图中。

相似度先对标注和输出做 Unicode NFKC 归一化并去除空白，再计算 `max(0, 1 - 编辑距离 / 标注长度)`，最后逐图平均。它不是通用准确率，也不衡量空格与换行。整图样本较少，100% 不代表真实场景总能正确识别。

计时使用 Intel Core i9-14900HX CPU 和 4 个 OCR 线程。每个方案对同一张 1080×201 的三行截图以新进程启动并识别，交替顺序重复 5 次，模型文件已进入系统缓存。计时包括 Python 启动和模型加载，不包括剪贴板、语言识别和翻译。PP-OCR 使用 RapidOCR 3.10.0 和 ONNX Runtime 1.32.0，关闭方向分类；EasyOCR 使用 CRAFT 检测及简体中文和英文识别。测试进程的 Python 网络连接被禁用。

模型大小不包含 Python、推理框架和运行内存。实验用 RapidOCR 环境约 388 MiB，包含其默认 Small 模型及测试依赖，并非接入现有项目的精确增量。初始测试过程中，Tiny 和 Small 的进程峰值 RSS 分别约 599 MiB 和 840 MiB，具体值受图片和环境影响。

## OCR 常驻性能对比（2026-11-24）

在同一台 Intel Core i9-14900HX 机器上，使用 CPU 和每个 OCR 引擎 4 个线程，对比宿主机每次加载 OCR 与临时 Docker 服务常驻 OCR。翻译使用已有的 Docker 常驻服务；临时 OCR 容器通过本机 Unix socket 接收图片。两边交替运行，各测 5 次，表中为中位数，括号为最小值和最大值。

| 模式 | OCR 每次加载 | OCR 常驻 | 图片翻译全流程：每次加载 → OCR 常驻 |
| --- | ---: | ---: | ---: |
| 速度优先：Tiny | 0.73 秒（0.72～0.78） | 0.22 秒（0.21～0.25） | 0.95 秒（0.92～1.02）→ 0.45 秒（0.43～0.48） |
| 效果优先：Small | 1.71 秒（1.65～1.79） | 1.05 秒（1.02～1.11） | 2.61 秒（2.59～2.73）→ 2.05 秒（1.93～2.17） |

全流程使用 1080×201 的三行中英混排图片文件，包含程序启动、OCR、翻译和输出，不包含读取剪贴板。另用 1684×918 的真实英文网页截图单独测试 OCR，Tiny 和 Small 均约节省 0.5 秒。同一模型在两种路径的 OCR 原文一致，PLaMo 译文存在少量措辞波动。

这组数字来自独立的 OCR 原型容器，模型已预热；正式服务的实现、设备、图片与系统负载可能产生不同结果。该原型中两个 OCR 模型都使用过后，进程驻留内存约 220 MiB；这不是正式集成的固定增量。常驻主要避免重复导入 OCR 依赖和初始化模型，图片推理及翻译仍需执行。

### 正式服务验证

同日将 OCR 接入 Docker 常驻服务后，使用同一张 1080×201 图片，在旧服务和隔离的新服务之间交替测试各 5 次；模型均已预热。结果为中位数，括号为范围：

| 模式 | OCR：原实现 → 常驻 | 图片翻译全流程：原实现 → 常驻 |
| --- | ---: | ---: |
| 速度优先：Tiny | 0.85 秒（0.80～0.87）→ 0.24 秒（0.23～0.30） | 1.12 秒（1.05～1.14）→ 0.51 秒（0.48～0.54） |
| 效果优先：Small | 1.89 秒（1.67～1.97）→ 1.14 秒（1.03～1.18） | 2.92 秒（2.75～2.96）→ 2.38 秒（2.20～2.61） |

两种实现输出的 OCR 原文一致。测试使用图片文件输入，未计入剪贴板读取；两个容器在同一台机器上运行，结果受当时资源占用影响。
